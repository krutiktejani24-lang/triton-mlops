# High-Throughput Multi-Model Serving with Triton Inference Server

**Domain:** Multi-Task AI / Healthcare-style analytics  
**Tech stack:** NVIDIA Triton Inference Server · ONNX · gRPC + REST · Docker (CPU)

Two different models are served **simultaneously by a single Triton instance**:

| Model | Type | Input | Output |
|---|---|---|---|
| `churn_model` | Tabular MLP (ONNX) | 8 customer features | `[P(stay), P(churn)]` |
| `digit_image_model` | Image classifier (ONNX) | 1×8×8 grayscale image | 10 class probabilities |

Each model has its own `config.pbtxt` with **dynamic batching** and **two CPU instances**.
A browser dashboard and a command-line client call the server over **both REST and gRPC**,
with many concurrent requests coming from a single client application.

```
 Browser ──► Flask dashboard ──┬─ REST  :8000 ─┐
 CLI client (demo_client.py) ──┴─ gRPC  :8001 ─┴─► Triton ─┬─ churn_model        (2 CPU instances, dyn. batching)
                                                           └─ digit_image_model  (2 CPU instances, dyn. batching)
```

## Run it

### Option A – Docker (real Triton, recommended)

```bash
docker compose up --build
```

Open **http://localhost:5006**. The first start downloads the Triton image (~10 GB, CPU only is fine).
Triton endpoints: REST `localhost:8000`, gRPC `localhost:8001`, metrics `localhost:8002`.

### Option B – Dashboard only (no Docker, "demo mode")

```bash
pip install -r requirements.txt
cd app && python server.py          # then open http://localhost:5006
```

Without Triton the gateway runs the same ONNX files with ONNX Runtime and shows an
orange *Demo mode* badge. As soon as Triton is up the badge turns green (*Triton LIVE*) automatically.

### Retrain / re-export the models (optional – ONNX files are already included)

```bash
pip install -r requirements.txt
python scripts/export_models.py
```

### Command-line client (REST + gRPC + concurrent test)

```bash
python client/demo_client.py --requests 1000 --workers 64
```

Quick health checks while Triton is running:

```bash
curl -s localhost:8000/v2/health/ready -o /dev/null -w "%{http_code}\n"   # 200
curl -s localhost:8000/v2/models/churn_model | python -m json.tool
curl -s localhost:8000/v2/models/churn_model/stats | python -m json.tool
```

## What the dashboard shows

* **Churn predictor** – sliders → live prediction from Triton.
* **Digit classifier** – draw on the 8×8 grid or load a real test image → live prediction.
* **REST / gRPC switch** – the whole page flips protocol; latency is shown per call.
* **Concurrent load test** – hundreds of parallel requests to *both* models at once;
  throughput, p50/p95/p99 latency and a latency histogram.
* **Server statistics** – from Triton's stats API: inferences vs. executions and batch-size
  distribution. *Avg batch > 1 = dynamic batching is working.*
* **Config viewer** – the `config.pbtxt` of each model.

## Key configuration (per model)

```
max_batch_size: 32
instance_group [ { count: 2  kind: KIND_CPU } ]            # 2 parallel model instances
dynamic_batching { preferred_batch_size: [4, 8, 16]
                   max_queue_delay_microseconds: 1000 }     # wait ≤1 ms to merge requests
```

## Results (from `export_models.py`)

| Model | Metric |
|---|---|
| churn_model | accuracy 0.82, ROC-AUC 0.87 (synthetic customer data) |
| digit_image_model | accuracy 0.98 (sklearn 8×8 digits, held-out set) |

ONNX outputs match the original scikit-learn models to < 1e-6.

## Notes

* The churn data is synthetic (generated by a known rule + noise) – it demonstrates serving, not clinical accuracy.
* Models are exported with a small hand-written ONNX serializer so the export needs only
  `numpy`, `scikit-learn` and `onnxruntime`. You can swap in `skl2onnx` / PyTorch export if you prefer.
* To use a GPU later, change `kind: KIND_CPU` to `KIND_GPU` and run Triton with `--gpus all`.
